# Правки и дополнения к ТЗ HobbyHub (v1.0 → v1.1)

Документ фиксирует решения по замечаниям, найденным при ревью исходного ТЗ
(«Техническое задание на разработку MVP C2C маркетплейса развлекательных услуг»).
Нумерация пунктов соответствует ревью; ссылки — на разделы/FR исходного документа.

Статус: предложено, требует подтверждения бизнес-стороной по пунктам 1, 2, 4, 15
(юридические/продуктовые решения, не чисто технические).

---

## Критично — юридические и бизнес-риски

### 1. Юридическая база эскроу (относится к разделу 4.5, FR-5.1–5.2)

**Было:** «Холдирование средств (если провайдер поддерживает) или перевод на
специальный счёт платформы» — без юридического оформления.

**Решение:**
- Использовать готовую продуктовую схему провайдера (ЮKassa «Безопасная сделка» /
  сплитование выплат) — платформа не хранит деньги напрямую, провайдер выступает
  агрегатором.
- Заключить с каждым продавцом агентский договор (оферта при регистрации:
  продавец назначает платформу агентом по приёму средств за его счёт).
- Номинальный счёт в банке — отклонён как избыточный для MVP при среднем чеке
  C2C-услуг.

**Действие:** добавить шаг «юридическое оформление агентской схемы» в Фазу 4,
согласовать текст оферты с юристом до интеграции платежей.

### 2. Чеки 54-ФЗ vs самозанятые (FR-5.2)

**Было:** «Чек покупателю (54-ФЗ — через провайдера)» — не учитывает, что
самозанятые формируют чек через приложение «Мой налог», а не через кассу 54-ФЗ.

**Решение:** использовать провайдера с готовой интеграцией под самозанятых
(ЮKassa/Тинькофф имеют такие продукты) — платформа не строит прямую интеграцию
с API ФНС на MVP. Фоллбэк: продавец пробивает чек сам, платформа блокирует вывод
средств до появления номера чека, привязанного к заказу.

**Действие:** уточнить у выбранного провайдера конкретный продукт до старта Фазы 4.

### 3. GDPR исключён из требований (раздел 5.3)

**Было:** упомянут GDPR при том, что раздел 13 ограничивает платформу
территорией РФ — несогласованность скоупа.

**Решение:** убрать GDPR. Оставить требование по 152-ФЗ и **добавить явное
требование локализации персональных данных пользователей РФ на серверах на
территории РФ** (в исходном ТЗ это требование отсутствовало).

### 4. Верификация продавца перед выплатами (FR-9.1, FR-5.5)

**Было:** верификация продавца помечена «опционально для MVP», хотя провайдер,
вероятно, требует KYC перед выплатами по маркетплейс-схеме.

**Решение:** верификация обязательна **перед первым выводом средств**, но не
перед публикацией объявления (не блокирует рост каталога на старте).

**Действие:** подтвердить фактическое требование у провайдера при выборе схемы
из п. 1.

## Технические дополнения

### 5. Защита от гонок при бронировании (новый FR, дополняет 4.4)

**Добавить FR-4.5:** создание брони выполняется в транзакции с уникальным
ограничением на `(seller_id, booking_date, start_time)` для заказов в статусах
`pending / confirmed / paid`. Опционально — короткая Redis-блокировка слота как
барьер перед обращением к БД в пиковой нагрузке.

### 6. Тайм-аут оплаты (дополняет FR-4.4)

**Добавить:** статус «Ожидает оплаты» имеет TTL 30 минут. По истечении —
автоматическая отмена заказа и освобождение слота (scheduled job).

### 7. Идемпотентность и подпись вебхука (дополняет FR-5.2)

**Добавить:**
- уникальный constraint на `provider_transaction_id` в таблице `transactions`
  (повторный вебхук — upsert без побочных эффектов);
- обязательная проверка подписи вебхука перед обработкой.

### 8. Минимальный лид-тайм бронирования (дополняет FR-4.1/4.2)

**Добавить:** нельзя забронировать слот, начинающийся раньше чем через 12 часов
от текущего момента. Причина: иначе 24-часовой тайм-аут подтверждения продавца
(FR-4.3) может истечь позже времени оказания услуги.

### 9. Резервное копирование БД (дополняет раздел 5.4)

**Добавить:** managed PostgreSQL с автоматическими бэкапами и point-in-time
recovery (Yandex Managed PostgreSQL — единый облачный провайдер с остальной
инфраструктурой).

## Исправление внутренних противоречий

### 10. Условная обязательность цены (FR-2.1, схема `services`)

**Было:** поле «Цена» помечено безусловно обязательным, при этом один из типов —
«по договорённости».

**Решение:** `price_min` / `price_max` — nullable, обязательны только при
`price_type != 'negotiable'`. UI скрывает числовые поля при выборе «по
договорённости».

### 11. Унификация целевой нагрузки (раздел 5.1 vs 11.1)

**Было:** заявлена поддержка 1000 одновременных пользователей (5.1), но
нагрузочный тест проверяет только 500+ (11.1).

**Решение:** нагрузочное тестирование проводится на целевые 1000+ пользователей.

### 12. Финальный выбор карт-провайдера (раздел 4.3, 6.2)

**Было:** перечислены три альтернативы (Yandex Maps / Google Maps /
Leaflet+OSM) без окончательного решения.

**Решение:** зафиксировать **Yandex Maps JS API** как единственный вариант для
MVP (лучшее геокодирование адресов РФ). Абстракция под мультипровайдерность не
закладывается.

## Продуктовые дополнения (уточнить с бизнесом)

### 13. Односторонние отзывы (FR-7.1)

**Решение для MVP:** оставить только «покупатель → продавец». Добавить это как
явное ограничение в раздел 13 («Ограничения MVP»). Двусторонние отзывы —
кандидат на пост-MVP.

### 14. Обработка неявки (no-show)

**Решение для MVP:** отдельный статус заказа не вводится — неявка обрабатывается
через существующий механизм «Спор» (раздел 4.5, FR-9.3). В критерии решения
администратора добавить: при неявке основанием для решения служит переписка в
чате, привязанная к заказу.

### 15. Продавцы-команды (раздел 13, допущение «один продавец = одно физлицо»)

**Решение:** сохранить юридическую модель «один аккаунт продавца = один
самозанятый», но добавить в профиль продавца необязательное поле «название
студии/бренда» — визуально закрывает часть рынка команд без усложнения
мультиаккаунтной архитектуры.

## Сводка изменений в структуре БД (Фаза 1 затрагивает только `users`)

- `services.price_min`, `services.price_max` → `nullable` (п. 10)
- `transactions.provider_transaction_id` → `unique` (п. 7, потребуется в Фазе 4)
- `bookings` → unique constraint `(seller_id, booking_date, start_time)` для
  активных статусов (п. 5, потребуется в Фазе 3)
- `users.brand_name` → новое nullable-поле (п. 15)
