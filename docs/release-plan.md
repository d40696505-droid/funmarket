# План релиза HobbyHub

Статус на 2026-08-28. Документ описывает путь от текущего состояния до
публичного запуска в продакшене. Дополняет `docs/tz-amendments.md` —
юридические и продуктовые решения оттуда здесь не повторяются, только
переносятся в конкретные шаги.

## 0. Текущее состояние — что уже готово

Функционально MVP закрывает весь исходный скоуп: регистрация/auth,
каталог с поиском/фильтрами/картой, бронирование по слотам и по запросу
(включая групповую вместимость), эскроу-платежи (за абстракцией
`PaymentProvider`), отзывы, чат (включая плавающий виджет и канал
поддержки), избранное, модерация объявлений админом, профили продавцов,
уведомления.

С 2026-08-27 сайт живёт не на dev-сервере за туннелем, а на выделенном
сервере (Timeweb) под собственным доменом **hobbyhub.ru**, с настоящим
TLS-сертификатом (Let's Encrypt через Caddy, автообновление). Backend и
frontend собраны в прод-режиме и запущены через systemd под отдельным
непривилегированным пользователем `hobbyhub` (не root). По итогам
аудита безопасности 2026-08-27 закрыт ряд находок (детали — Фаза 5).
Пока нет реального платёжного провайдера — оформление брони временно
выключено флагом `ORDERS_DISABLED` (сайт открыт для просмотра/регистрации,
проверки UX и контента, но без реальных сделок).

Это значит, что релиз — это в основном не «дописать функциональность»,
а закрыть юридические, платёжные и надёжностные пробелы ниже.

## 2. Фазы

### Фаза 0 — Юридическая и бизнес-подготовка
Блокирует Фазу 4 (платежи) и публичный анонс.

**Черновики готовы (2026-08-28):** `docs/legal/` — пользовательское
соглашение, политика ПДн (152-ФЗ), оферта агентской схемы, условия для
продавцов (+ `.docx`-версии). Это AI-черновики на основе решений из
`docs/tz-amendments.md`, **не готовы к публикации без юриста** — в каждом
файле внизу список `{{ПЕРЕМЕННЫХ}}` под конкретные реквизиты/провайдера
и отдельно отмечено, где решение чисто юридическое, а где ещё и требует
доработки кода (шкала штрафов за отмену брони, дедлайн подтверждения
заявки).

- Подтвердить у бизнеса пункты 1, 2, 4, 15 из `docs/tz-amendments.md`
  (агентская схема эскроу, чеки для самозанятых, обязательность
  верификации продавца перед выплатами, модель «один продавец = одно
  физлицо + бренд-имя»).
- Выбрать реального платёжного провайдера (ЮKassa «Безопасная сделка»
  или аналог с поддержкой самозанятых), заключить договор — от этого
  зависит финальный текст `agency-offer.md` (у провайдера обычно есть
  готовый шаблон под их продукт).
- Отдать черновики из `docs/legal/` юристу на проверку, заполнить
  реквизиты, опубликовать на сайте (сейчас на сайте нет страниц с этими
  документами — понадобится доработка фронтенда, когда тексты будут
  готовы).
- Определить юрлицо/ИП площадки, налоговый режим, реквизиты.
- Подать уведомление в Роскомнадзор об обработке ПДн (после регистрации
  юрлица, до начала реальной обработки данных пользователей).

### Фаза 1 — Инфраструктура и деплой

**Готово (2026-08-27):** переезд на выделенный сервер (Timeweb) —
`scripts/server-bootstrap.sh` (Node/PostgreSQL+PostGIS/MinIO/Caddy/ufw/
непривилегированный пользователь `hobbyhub`, идемпотентно) +
`scripts/deploy.sh` (git clone/pull, сборка, миграции, systemd-юниты,
Caddyfile под домен). ~~Домен + TLS~~, ~~backend/frontend под root~~ —
оба закрыты этим же переездом (backend/frontend теперь `User=hobbyhub`,
не root). Пошаговая шпаргалка по типовым операциям — `docs/server-cheatsheet.md`.

Осталось:
- Хостинг: рассмотреть managed-сервисы (уже рекомендовано в
  tz-amendments п.9) — Managed PostgreSQL с автобэкапами и PITR,
  S3-совместимое хранилище вместо self-hosted MinIO. Не блокирует
  запуск при разумном трафике, но снижает риск при росте нагрузки —
  решить по факту, не обязательно до первого релиза.
- CI/CD (GitHub Actions, раз репозиторий уже на GitHub): lint + typecheck
  + build на каждый PR, ручной или автоматический деплой на push в main
  (сейчас деплой — ручной запуск `deploy.sh` по SSH).
- Секреты: сейчас `.env` с правами 600, свежесгенерированы при
  bootstrap — приемлемо для старта; секрет-менеджер хостинг-провайдера
  можно добавить позже, не блокер.
- resource limits в systemd-юнитах (сейчас без ограничений по
  памяти/CPU) — желательно перед реальной нагрузкой, не блокер MVP.

### Фаза 2 — Надёжность данных
- Проверить и протестировать восстановление из бэкапов БД (не просто
  включить автобэкап, а реально прогнать restore на staging).
- Бэкап object storage (фото услуг, аватары, фото в отзывах).
- Health-check эндпоинты + аптайм-мониторинг + сбор ошибок (Sentry или
  аналог) — сейчас никакого мониторинга ошибок в проде нет.
- Логирование: структурированные логи backend с ротацией.

### Фаза 3 — Email

Ранее откладывали до появления домена (SPF/DKIM/DMARC не настроить без
него) — теперь домен есть (`hobbyhub.ru`), блокер снят, можно начинать.

- Подключить реального провайдера (SendGrid / Mailgun / Yandex Cloud
  почтовый сервис) вместо `mail.service.ts`-заглушки — интерфейс методов
  менять не нужно, только реализацию (например, через `nodemailer` + SMTP,
  настраиваемое через env — `SMTP_HOST/PORT/USER/PASSWORD/MAIL_FROM`).
- Настроить SPF/DKIM/DMARC для `hobbyhub.ru` (DNS-записи у регистратора
  или через NS-хостинг Timeweb, куда уже переключены NS-серверы домена),
  иначе письма будут попадать в спам.
- До подключения провайдера можно проверить саму реализацию на бесплатном
  тестовом SMTP вроде Ethereal Email — письма никуда не уходят, но код и
  flow проверяются end-to-end.

### Фаза 4 — Реальные платежи
Возможна только после Фазы 0. До этой фазы бронирование скрыто флагом
`ORDERS_DISABLED` (backend `.env`) / `NEXT_PUBLIC_ORDERS_DISABLED`
(frontend `.env.local`) — сайт открыт для просмотра/регистрации, но
попытка оформить бронь показывает «сайт в разработке». Снимается без
правок кода — убрать обе переменные и передеплоить.
- Реализовать реальный класс `PaymentProvider` вместо
  `MockYookassaProvider` — архитектурно уже готово (весь остальной код
  работает через интерфейс, подстановка класса под токеном
  `PAYMENT_PROVIDER` не требует правок в бронированиях/эскроу-логике).
- Реализовать флоу верификации продавца перед первой выплатой (поле
  `isSellerVerified` в модели уже есть, самого KYC-процесса — нет).
- Прогнать сквозной тест реальных платежей в sandbox-режиме провайдера
  перед боевым переключением.

### Фаза 5 — Тестирование и безопасность

**Готово (2026-08-27):** полный аудит безопасности перед релизом (auth/authz,
инъекции, загрузка файлов, секреты, CORS, rate limiting, эскроу-логика,
админка, зависимости). Найденное и исправленное:
- Basic Auth гейт обходился подделкой `Authorization: Bearer x` — гейт
  снят полностью (см. блокер №4 выше).
- Токены сброса пароля/подтверждения email писались в лог в открытом виде
  в проде — теперь логируются только вне `NODE_ENV=production`
  (`backend/src/mail/mail.service.ts`); сама отправка писем по-прежнему
  не реализована (см. Фазу 3).
- WebSocket `chat:join` пускал в комнату любого чата без проверки, что
  пользователь — участник (можно было слушать чужую переписку по
  известному chatId) — добавлена проверка через `getChatForParticipant`
  (`backend/src/chats/chats.gateway.ts`).
- Presigned upload в MinIO принимал `Content-Type` по префиксу `image/`
  (пропускал `image/svg+xml` — потенциальный stored XSS) — заменено на
  точное совпадение (`backend/src/uploads/uploads.service.ts`).
- `fixedAmount` при подтверждении брони с договорной ценой не проверялся
  на положительность — добавлена валидация
  (`backend/src/bookings/dto/confirm-booking.dto.ts`).
- `npm audit` (backend и frontend) — 0 уязвимостей после `npm audit fix`.

Не исправлено, осознанно отложено:
- Внешние URL для аватара/фото услуг/фото отзывов не ограничены доменом
  собственного хранилища (можно подменить контент после модерации) —
  требует решения, ограничивать ли строго `S3_PUBLIC_URL` или разрешить
  внешние ссылки как фичу.
- `accessToken`/`refreshToken` в `localStorage` вместо `httpOnly`-cookie —
  архитектурная правка, требует отдельного захода.
- Нет `helmet`/security headers в backend, нет rate limit на
  `/api/auth/refresh`, MinIO service-account с `readwrite` на весь
  инстанс вместо одного бакета — низкий приоритет, до релиза не блокирует.

- Написать smoke/e2e-тесты на критичные пути (регистрация, бронирование,
  оплата, чат) — сейчас в проекте нет тестов, кроме дефолтного
  Nest-boilerplate (`app.controller.spec.ts`).
- Нагрузочное тестирование на целевые 1000+ одновременных пользователей
  (зафиксировано в tz-amendments п.11).
- Security review: OWASP top 10, аудит прав доступа (`JwtAuthGuard`,
  admin-гварды), проверка что секреты не попали в git, что Basic Auth
  гейт действительно снят.
- Ручной регресс по ключевым пользовательским сценариям (чек-лист ниже).

### Фаза 6 — Контент и запуск
- Очистить тестовые данные (услуги вида «Скриншот-тест…», тестовые
  аккаунты) перед показом реальным пользователям.
- Убедиться, что модерация объявлений отработана на реальном потоке
  (сам механизм уже реализован).
- Мягкий запуск: ограниченный круг пользователей/один город перед
  широким анонсом.
- План отката: как быстро откатить деплой/миграцию при критичном баге.

### Фаза 7 — После запуска
- Мониторинг первую неделю: ошибки, конверсия регистрация → бронирование
  → оплата.
- Возврат к пост-MVP пунктам из tz-amendments («продуктовые дополнения»:
  двусторонние отзывы и т.п.) и к остальным пожеланиям из бэклога.

**Готово:** канал поддержки пользователей — реализован поверх
существующего чата. Один аккаунт помечается флагом `User.isSupport`
(сейчас — напрямую в БД, тем же способом, что и `isAdmin`; отдельной
админ-панели управления пользователями в проекте нет). Публичный
эндпоинт `GET /api/support/contact` отдаёт его id, плавающий
чат-виджет показывает закреплённую строку «Поддержка» сверху списка
диалогов — переиспользует уже готовую инфраструктуру чата (WS,
REST-фолбэк, бейдж непрочитанных), отдельной системы тикетов не
потребовалось. На новом сервере поддержку сейчас ведёт аккаунт
`support@hobbyhub.ru` — перед реальным запуском решить, кто и по какому
графику на него отвечает (или завести несколько таких аккаунтов, если
нагрузка потребует).

## 3. Чек-лист регресс-тестирования перед запуском (минимум)

- Регистрация покупателя и продавца, подтверждение email, вход, сброс
  пароля.
- Создание услуги продавцом → прохождение модерации → публикация.
- Поиск/фильтрация в каталоге, просмотр на карте.
- Бронирование по слотам (включая групповую вместимость) и по запросу.
- Полный цикл оплаты: холдирование → подтверждение продавцом →
  освобождение эскроу → чек покупателю.
- Отмена брони, спор, разрешение спора администратором.
- Чат: сообщения, жалоба на сообщение, плавающий виджет и полная
  страница.
- Отзыв после завершения заказа, ответ продавца на отзыв.
- Избранное: добавление, счётчик у продавца.
- Админ-панель: модерация, при необходимости — управление пользователями.

## 4. Порядок фаз

Фазы 0 и 1 можно вести параллельно (юридическая подготовка не блокирует
инфраструктурную). Фаза 4 (реальные платежи) требует завершённой Фазы 0.
Фазы 2, 3, 5 — после Фазы 1. Фаза 6 — после того, как закрыты все пункты
раздела 1 (жёсткие блокеры). Фаза 7 — постоянная, начинается сразу после
запуска.
